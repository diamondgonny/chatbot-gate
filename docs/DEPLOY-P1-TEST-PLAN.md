# 배포 P1 수정 인수 테스트 계획

백엔드 Blue-Green 배포의 P1 세 건에 대한 수정·검증 기준이다. 코드 위치는 기준 커밋 `6598cea`를 따른다. 중복 시나리오는 공통 테스트로 묶되, 각 행에 나열한 입력 사례는 모두 검증한다.

## 대상과 정책

| 문제 | 코드 위치 |
|---|---|
| P1-1: 전환·롤백 실패를 성공 처리하고 서빙 컨테이너를 삭제 | `deploy-blue-green.sh:406-421`, `:436`, `:470` |
| P1-2: CI의 이동 태그 선택과 상태 파일의 VERSION 덮어쓰기로 검사·배포 이미지 불일치. 버전을 지정한 롤백도 무시되고 성공으로 끝남 | `ci-cd.yml:83-108` / `deploy-blue-green.sh:247` |
| P1-3: 전환 후 상태 저장까지의 중단 또는 동시 배포로 상태 불일치·서빙 컨테이너 삭제 | `deploy-blue-green.sh:330`, `:616-638` / 워크플로 동시 실행 |

P1-4(전환이 Caddy의 실행 중 설정에만 남아, Caddy 재시작·리로드 뒤 upstream이 예전 환경으로 돌아가는 문제)는 이번 범위에서 뺀다. 운영 Caddy 설정은 당분간 그대로 쓰고, 전환 수단도 지금처럼 admin API PATCH다. 세 건의 수정이 이 동작을 만났을 때의 처리는 C1·A7에서 확인하고, 남는 위험은 잔여 위험에 적는다.

- **upstream 확인**: 실제 upstream은 admin API로 조회한 dial이다. Caddy가 재시작·리로드로 Caddyfile을 다시 읽으면 dial이 `chatbot-gate-backend-{env.ACTIVE_ENV}:4000` 자리표시자로 돌아가며(운영에서 마지막 배포 뒤 관찰됨, 2026-10-09), 이때는 Caddy 컨테이너의 `ACTIVE_ENV` 값으로 해석한다. PATCH의 적용 여부도 응답이 아니라 이 조회로 판정한다.
- **식별자**: `/health` 응답에 `env`(컨테이너의 `DEPLOYMENT_ENV`)와 `build`(이미지에 넣은 빌드 커밋)를 추가한다. 같은 커밋을 다시 빌드한 이미지는 `build`가 같으므로, 요청 digest와의 일치는 컨테이너 이미지 조회로 따로 확인한다.
- **전환·롤백**: 전환 전에 Caddy 컨테이너에서 새 컨테이너로 직접 조회해 도달성과 환경·빌드를 확인한다. 전환·롤백 뒤에는 실제 upstream과 Caddy 경유 응답의 환경·빌드를 모두 확인한다. 복귀를 확인한 뒤에만 실패한 새 환경을 정리한다. 복구 여부가 불확실하면 양쪽을 보존하고 실패한다.
- **상태**: 실제 upstream이 단일 Blue/Green으로 확정되고 내부·Caddy 경유 검증과 이미지 확인을 통과하면 환경·digest를 함께 교정한다. 확인 불가 시 중단한다. 다만 상태와 upstream이 같은 환경을 가리키는데 그 환경이 죽었거나 없으면, 서빙이 없는 것으로 보고 복구 배포를 진행한다(C8). 전환 검증 직후 상태를 원자적으로 저장하고 구 환경을 정리한다. 저장 실패 시 롤백 없이 양쪽을 보존한다. 상태 파일은 정해진 키의 값만 읽고 셸로 실행하지 않는다. 운영 Caddy의 compose가 이 파일을 `env_file`로 읽으므로 `ACTIVE_ENV`·`INACTIVE_ENV` 키와 `키=값` 형식은 유지한다.
- **이미지**: 테스트·스캔·배포에 같은 완전한 digest 참조를 사용한다. 상태 파일과 `.env`의 과거 값으로 배포 입력을 덮어쓰거나 이동 태그로 대체하지 않는다. 이미지 정리는 배포 스크립트가 서버 잠금 안에서만 하고, 워크플로의 별도 정리는 없앤다.
- **잠금**: 서버 잠금 충돌은 즉시 실패한다. 배포와 자식 프로세스가 살아 있는 동안 잠금을 유지하고, 모두 종료되면 해제한다. CI도 배포를 직렬화하며 진행 중 실행을 취소하지 않는다. 늦게 도착한 오래된 실행이 최신 커밋의 배포를 밀어내지 않게 한다.
- **신호**: 신호를 받아도 PATCH·정지·삭제·상태 기록을 하지 않는다. 복구는 다음 실행의 상태 확인에 맡긴다.
- **종료 코드**: 0은 성공이다. 1은 실패했지만 서빙이 실행 전과 같다고 확인된 경우다. 변경 전 거부·중단과 확인된 롤백이 여기에 속한다. 2는 서빙이 실행 전과 달라졌거나 확인할 수 없어 사람의 확인이 필요한 경우다. 스크립트가 분류하지 않은 실패도 추가 변경 없이 2로 끝낸다. 전환·상태 저장 뒤의 정리 실패는 롤백하지 않고 경고와 함께 0으로 끝낸다.
- **컨테이너**: 정지·삭제는 upstream이 아님을 확인한 대상에만 수행하며, 확인은 명령 직전의 upstream 재조회로 한다. 아래 구분은 한 실행 안에서 컨테이너 ID로 추적한다. 이름이 같아도 재생성된 컨테이너는 다른 대상이다.

| 컨테이너 | 취급 |
|---|---|
| 시작 시 발견한 비서빙 컨테이너 | 조회 상태를 신뢰하지 않고 강제 삭제 완료 후 새로 생성 |
| 이번 실행에서 생성·검증한 컨테이너 | 전환 후보 |
| 시작 시 서빙했고 정지·삭제 명령을 보내지 않은 구 컨테이너 | 전환 후에도 롤백 후보 |
| 정지·삭제 명령을 이미 보낸 컨테이너 | 롤백 재사용 금지 |

Docker는 정지 대기 중에도 running·healthy로 보일 수 있다. 다음 실행에서 기존 비서빙 컨테이너를 삭제·재생성하는 방식으로 잔류 정지 요청을 다룬다. 별도의 실행 간 컨테이너 이력은 두지 않는다.

### 자동 배포 허용 규칙

배포 job 시작 시 자기 커밋과 원격 `main` 최신 커밋의 내용을 비교한다. 비교 경로는 워크플로 `paths`와 같은 `backend/**`, `.github/workflows/ci-cd.yml`이다. 두 커밋의 트리를 직접 대조하며 병합 기준(three-dot) 비교를 쓰지 않는다.

| 입력 | 결과 |
|---|---|
| 비교 경로 내용이 같음 | 허용. 문서·프론트엔드 후속 변경, 강제 푸시, 같은 커밋의 다른 digest 재빌드도 이 규칙 적용 |
| 비교 경로 내용이 다름 | 서버 변경 전에 거부. 빌드 시각·재실행 여부·Git 조상 관계는 고려하지 않음. 자주 생기는 정상 결과이므로 배포만 건너뛰고 job은 실패로 만들지 않음 |
| 최신 커밋 조회 또는 비교 실패 | 서버 변경 전에 중단, job 실패 |
| digest를 지정한 수동 실행 | 내용 비교 제외. 이후 자동 배포를 동결하지 않음 |

서버 직접 실행은 수동 배포이며 서버에 커밋 이력·소스 커밋 상태를 요구하지 않는다. CI 비교 통과 이후 새 푸시가 들어오는 틈은 허용한다. 이미 진행 중인 배포는 끝내고 다음 배포를 직렬 실행한다.

커밋 일치나 Git 조상 관계가 아니라 내용을 비교하는 이유는 이 레포의 작업 방식이다. 기준 커밋 시점의 최근 CI 실행 10건 중 5건의 커밋이 강제 푸시로 `main` 이력에서 사라졌고, 문서·프론트엔드 커밋이 백엔드 커밋 사이에 자주 낀다.

### 출시 순서

현재 `/health`는 식별자를 돌려주지 않는다(`app.ts:192`). 새 스크립트는 식별자 없는 컨테이너의 서빙·복귀를 확인할 수 없으므로 두 단계로 출시한다.

1. 식별자만 추가한 백엔드를 현행 파이프라인으로 먼저 배포한다.
2. 서버의 구 스크립트·compose·상태 파일을 백업하고, 병합할 커밋과 내용이 같은 새 스크립트·compose를 서버에 올려 해시를 확인한 뒤 워크플로를 병합한다. 이 병합의 실행이 첫 배포(C7)다.

구 파일로 되돌릴 때 상태 파일은 백업을 쓰지 않고 실제 upstream 기준으로 다시 쓴다. 새 방식 배포가 한 번이라도 성공했으면 백업의 `ACTIVE_ENV`가 낡은 값이고, 구 스크립트는 그 값을 믿고 서빙 컨테이너를 삭제한다.

서버 파일을 올린 뒤 병합 전까지 구 워크플로의 배포는 태그 입력이라 변경 전에 거부된다(B5). 식별자가 없는 과거 이미지로의 배포·롤백은 지원하지 않으며 전환 전에 거부한다(R1).

## 준비와 공통 판정

| 환경 | 용도 |
|---|---|
| L | 운영과 별도 Docker 데몬의 로컬 테스트. 상태·볼륨·잠금 경로도 분리 |
| WT | 실제 GitHub Actions에서 격리된 테스트 호스트·레지스트리로 실행. 플랫폼 연결 확인. 운영 비밀값이 없는 별도 테스트 저장소에 같은 워크플로를 두어, 테스트 실행이 운영으로 전달될 경로를 두지 않음 |
| WP | 운영 첫 정상 배포 관찰. 실패 주입·강제 중단·시험 롤백 없음 |

- L/WT는 운영과 같은 컨테이너·네트워크 이름을 사용하고, 운영 Caddy의 백엔드 사이트 구성을 재현한다. 호스트 매처·중첩 route, upstream의 `{env.ACTIVE_ENV}` 자리표시자, 상태 파일을 읽는 `env_file`, 능동 헬스 체크(`health_uri /health`, 10초 간격)가 여기에 든다. 운영 Caddy는 Cloudflare Tunnel 뒤에서 이 사이트를 HTTP로 받으므로(`http://api.chatbotgate.click`) Caddy 경유 요청은 Host 헤더를 맞춰 Caddy에 직접 보낸다.
- L/WT의 버전은 운영 채취값(2026-10-09)에 맞추고 스크립트는 Linux에서 실행한다. Docker Engine 29.8.1 / Compose 5.5.1, Caddy v2.10.2(`--resume` 없이 Caddyfile로 시작), bash 5.3이며 `flock`·`python3`·`curl`이 있다. 이미지 저장소는 `overlay2`이고, `docker image prune`이 태그 없이 digest로만 받은 미사용 이미지를 삭제한다.
- 이미지 A/B의 환경·빌드를 Caddy 경유 응답으로 구분한다. 운영에서 manifest digest와 로컬 image ID는 값이 다르므로 단순 문자열 비교하지 않는다.
- 로컬 Git 정책 시험은 임시 저장소·원격 저장소에서 **워크플로가 사용하는 동일 비교 코드**를 실행한다. 시험용으로 판정 로직을 따로 구현하지 않는다.
- WT에는 시험할 커밋의 스크립트·compose를 준비하고 해시를 확인한다.
- 각 입력 사례마다 종료 코드, upstream, 상태 파일, 요청·실행 digest, 컨테이너 ID와 stop/rm 기록, 주입 지점·시각을 남긴다. 잠금 시험은 프로세스 생존 여부도, WT/WP는 run ID·실행 파일 해시도 기록한다.
- 모든 거부·중단은 그 사례의 원인을 가리키는 사유를 출력해야 통과다. 다른 원인으로 실패하면 불합격이다. 수동 조치를 안내하는 사례는 출력된 명령을 L에서 그대로 실행해 복구되는지 확인한다.
- **공통 불변식**: 하네스는 컨테이너를 끝낼 수 있는 호출(stop·rm·재생성·down·restart)마다 실제 upstream을 독립적으로 조회한다. 대상이 서빙 중이면 사례와 무관하게 불합격이다. 대상 upstream 외 Caddy 설정이나 MongoDB 컨테이너가 바뀌어도 같다. 실패·롤백 경로를 포함한 전 사례에 적용한다.
- **하네스 자체 검증**: L 하네스가 완성되면 기준 커밋의 스크립트를 한 번 실행해 아래 재현 기록의 사례가 불합격으로 판정되는지 확인한다.

### 주입과 부하

Docker 호출은 테스트 `PATH`의 래퍼로, HTTP 응답은 테스트 프록시나 래퍼로 제어한다. 파일 저장은 비-root 사용자·권한·용량 제한 및 쓰기·교체 명령 래퍼로 제어한다. 단계 도달 신호를 확인한 뒤 재개하거나 프로세스를 종료하며, 임의 지연만으로 시점을 추정하지 않는다. 주입이 발생하지 않으면 시험 구성 실패다. 운영 코드에 테스트 전용 분기는 넣지 않는다.

지속 요청은 정상 전환·롤백·중단 복구에만 적용한다. 변경 직전부터 완료·복구 후까지 Caddy로 요청하며, 정상 경로의 5xx·연결 실패·시간 초과·응답 중단은 모두 0건이어야 한다. 전환 전 시작한 요청은 구 빌드 응답을 허용하고, 검증 완료 후 시작한 요청은 새 환경·빌드여야 한다. 의도적 장애에서는 오류를 기록하되 실패 감지와 복구 수단 보존을 판정한다.

### 수치 기준

| 항목 | 기준 |
|---|---|
| HTTP 요청 | 연결 1초, 전체 3초 제한 |
| 전환 검증 | 최대 5회, 요청 종료 후 2초 간격, 전체 30초 |
| 롤백 요청·복귀 검증 | 별도의 전체 30초 |
| 일시적 실패 | 연결 오류·시간 초과·5xx 합계 1회까지. 성공에는 최소 4회 성공과 마지막 검사 성공 필요 |
| 즉시 실패 | 4xx, 파싱 실패, upstream·환경·빌드 불일치 |
| 시간 오차 | 단계당 최대 5초. 응답 정지 시험은 검증 시작 후 35초 내 실패 판정, 롤백 포함 70초 내 실패 종료 |
| 지속 요청 | 초당 10회, 요청당 3초 제한, 완료·복구 후 5초까지 |
| 잠금 해제 | 관련 프로세스가 모두 종료된 후 5초 내 새 잠금 획득 가능 |

전환과 롤백에 같은 검증 기준을 적용한다. 둘의 결과에 따른 정리 동작은 각각 시험한다.

## P1-1 전환·롤백

### 중단 후 재실행

아래 모든 지점에서는 배포 프로세스 그룹을 **SIGKILL**한 뒤 재실행한다. **SIGTERM**은 PATCH 직전과 전환 검증 중 두 대표 지점에서 추가하고, 신호 뒤에 PATCH·정지·삭제·상태 기록이 없음을 래퍼 기록으로 확인한다. 부모만 종료하는 잠금 시험은 C5, 실제 연결 단절은 C9, 잔류 정지 요청은 C10에서 확인하며 모든 지점에 조합을 반복하지 않는다. 특정 단계에 별도 종료 처리가 생기면 그 분기에만 시험을 추가한다.

| 중단 지점 | 재실행 판정 |
|---|---|
| PATCH 직전 | 구 서빙 환경 보호 |
| PATCH 적용 직후·응답 확인 전 / 전환 검증 중 / 검증 완료 후·저장 전 | 실제 upstream부터 확인. 과거 상태만 믿고 새 서빙 환경을 삭제하지 않음 |
| 임시 상태 파일 일부 작성 후 / 교체 직전 | 기존 파일 온전, 임시 파일 무시 |
| 상태 파일 교체 직후 | 환경·digest가 함께 저장된 완전한 새 상태 확인 |
| 구 환경 정리 중 / 직후 | 현재 서빙 환경 보호, 남은 비서빙 컨테이너는 컨테이너 정책대로 취급 |

재실행은 자동 복구 또는 사유를 밝힌 안전한 중단을 허용한다. 검증하지 않은 성공 기록·서빙 컨테이너 삭제는 금지한다. C10은 원격 프로세스 종료 직후와 이전 정지 제한시간 이후에 각각 재실행해 확인한다.

## 완료 조건과 범위

- L의 각 입력 사례를 자동화해 통과한 뒤 WT를 실행한다. 같은 실행에서 여러 검증을 함께 수집할 수 있으나, 실행하지 않은 입력은 미실행으로 기록한다.
- WP는 출시 순서 2단계의 첫 정상 배포에서 B1을 관찰한다. 실행 파일 해시·digest·상태·후속 정리 증거를 남기고 사람이 지켜본다.
- WT 호스트가 없으면 임시 호스트를 마련한다. 실패 주입을 운영에서 대신하지 않으며, WT 미실행 상태로 인수 완료를 선언하지 않는다.
- 완료 보고는 **“정의한 P1 인수 기준 통과”**로 표현하고 아래 잔여 위험을 함께 기재한다.

**잔여 위험(P1-4):** 운영 Caddy는 재시작·리로드·재부팅 때마다 upstream을 Caddy 컨테이너 생성 시점의 `ACTIVE_ENV`(상태 파일에서 읽은 값)로 되돌린다. 그 환경이 이미 정리됐으면 백엔드가 응답하지 못하고, 배포 스크립트는 이를 자동으로 복구하지 않고 중단한다(C1). 그때는 Caddy 컨테이너를 재생성해 상태 파일을 다시 읽힌다(A1). 재생성하는 동안 Caddy의 다른 사이트도 잠시 끊긴다. 되돌아간 환경이 정지 중인 구 컨테이너이면 다음 실행이 곧 종료될 대상을 healthy한 서빙 환경으로 오인할 수 있다. 이 문제의 해결과 시험은 이번 범위에서 제외한다.

**P2로 이관:** 느린 일반 요청의 종료 유예 내 완료 보장과 배포 중 Council 작업의 종료·재연결. 후자는 신규 작업 차단, 5분 내 완료 또는 취소·부분 저장 후 전환 기준으로 별도 검증한다. 운영 파일 동기화 자동화와 보안 스캔의 배포 차단(현재 Trivy는 `exit-code`가 없어 취약점이 나와도 통과)도 P2다. 그 외 P2도 이번 범위에 포함하지 않는다.

## 기준 커밋 재현 기록

기준 커밋의 스크립트 원본을 가짜 `docker`로 실행해 확인했다(2026-10-09). 실제 Docker·운영에는 접근하지 않았고, 전송 명령이 HTTP 상태와 무관하게 0으로 끝난다는 전제는 모델링한 것이다. 운영 서버의 스크립트·compose는 기준 커밋과 해시가 같다.

| 문제 | 입력 | 결과 | 대응 사례 |
|---|---|---|---|
| P1-1 | 전환 PATCH가 500으로 미적용 | `Traffic switched` 출력, 실제 upstream인 구 환경 정지·삭제, 종료 코드 0 | A2 |
| P1-1 | 새 환경 검증 실패 후 롤백 PATCH가 500으로 미적용 | `Rollback complete` 출력, 실제 upstream인 새 환경 삭제, 종료 코드 1 | A4 |
| P1-1 | 새 컨테이너가 `caddy_upstream` 네트워크에 없음 | `:221-223`의 비교식이 오류로 끝나 검사를 통과, 배포 성공 처리 | R1 |
| P1-2 | 입력 `VERSION=main-abc1234`, 상태 파일 `VERSION=main` | pull·compose 모두 `:main` 사용, 상태 파일도 다시 `main`, 종료 코드 0 | B2 |
| P1-3 | 전환 검증 중 SIGKILL 후 재실행 | 상태는 구 환경, 실제는 새 환경. 재실행이 `:330`에서 서빙 컨테이너 삭제. 새 컨테이너가 뜨지 못하면 종료 코드 1과 서빙 중단 | 중단 후 재실행 |
| P1-3 | 첫 실행의 전환 검증 중 두 번째 실행 시작 | 두 번째 실행이 방금 전환된 서빙 컨테이너 삭제. 첫 실행의 검증이 통과하면 둘 다 종료 코드 0 | C5 |

CI가 고르는 태그가 `:main`이라는 점은 metadata-action의 정렬 규칙(priority 내림차순: ref 600, raw 200, sha 100)으로 확인했다. 실행 로그는 보존 기간이 지나 확인하지 못했다.
